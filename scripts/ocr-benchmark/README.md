# 品名 OCR の比較

長いレシートを縮小したときの品名の変化を、スーパー・飲食店・コンビニを想定した各 10 品の合成画像で比較します。実際の写真や Pixel 4 での測定ではありません。

## 実行

Node.js とプロジェクトの依存関係に加え、Python 3、Pillow、日本語フォント `NotoSansCJK-Regular.ttc` が必要です。Ubuntu では `python3-pil` と `fonts-noto-cjk` が該当します。初回の OCR では Tesseract.js が日本語・英語の言語データをダウンロードします。通常の `npm test` からは実行しません。

リポジトリのルートから実行します。

```sh
python3 scripts/ocr-benchmark/generate.py /tmp/reciwake-ocr-benchmark
node --import tsx scripts/ocr-benchmark/run.mjs /tmp/reciwake-ocr-benchmark
```

フォントが別の場所にある場合は、生成コマンドに `--font /path/to/NotoSansCJK-Regular.ttc` を加えてください。生成画像・正解データ・言語キャッシュ・結果の JSON は指定した一時ディレクトリに保存されます。写真のアップロードは行いません。

## 比較条件

元画像は 900 × 2700 px、品名は 30 px のフォントで描画し、弱いぼかしと最大 0.25 度の傾きを加えています。次の両条件とも画素数上限は 192 万画素です。

| 条件     | 長辺上限 | 出力画像                    |
| -------- | -------- | --------------------------- |
| baseline | 1600 px  | 533 × 1600 px、JPEG 品質 88 |
| detail   | 3200 px  | 800 × 2400 px、PNG          |

両条件とも同じ現在の `parseReceipt`、Tesseract.js の既定モデル、日本語＋英語、OEM 1、PSM 6 を使用します。画像縮小は Pillow の LANCZOS を使うため、ブラウザーの `createImageBitmap` と画素単位の一致は保証しません。アプリの撮影・前処理経路全体の検証にはブラウザーでの確認が必要です。

品名は各画像内で重複しない価格で正解と対応付け、NFKC 正規化と空白除去の後に完全一致と文字の編集距離を計算します。価格を読み違えた品は未検出として扱います。表示上の空白の正しさは評価しません。合計金額は別に比較し、OCR の生テキストも結果に残します。

## 2026-09-29 の結果

円記号がバックスラッシュとして認識される場合への対応を含む現在のパーサーで、baseline は **23 / 30 品完全一致、文字誤り率 8.94%（21 / 235 文字）**、detail は **27 / 30 品完全一致、文字誤り率 1.70%（4 / 235 文字）** でした。合計金額は両条件とも 3 / 3 件一致しました。

修正前のパーサーを使用した当初の baseline は 11 / 30 品、文字誤り率 14.04% でした。この差には画像処理に加えて、品名末尾に付いた円記号の誤認識を取り除く効果が含まれます。

デスクトップ Node.js で各条件の 3 枚を単一ワーカーで順に読んだ計測では、baseline が約 3.03 秒・最大 RSS 約 190 MiB、detail が約 3.35 秒・約 193 MiB でした。初回ダウンロード時間を含まず、モバイルブラウザーの所要時間やメモリ量を示す値ではありません。

追加で比較した日本語単独モデル、浮動小数点版の `tessdata_best`、PSM 4 には、この画像群で一貫した改善がありませんでした。日本語単独では価格の区切りも誤認識したため、既定の日本語＋英語と PSM 6 を維持しています。

この小さな合成画像群だけで実際のレシート全般の精度は保証できません。実写のかすれ、照明、折り目、ピントなどは別途評価が必要です。

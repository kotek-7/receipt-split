# レシート読み取りの調査と評価

調査・測定日: 2026-10-03

飲み会の買い出しや飲食店のレシートから、品名・数量・行金額・支払総額を取り出す。単に文字が読めるかだけでなく、単価と行金額を区別できるか、同じ商品が複数行あっても欠落しないか、預り金や釣銭を商品として扱わないかを評価する。

画像を直接読む Gemma を追加し、本番画面で評価した実写 holdout 11 枚では、金額・数量 F1 が従来の 27.27% から 85.00%、総額一致が 2/11 枚から 10/11 枚になった。品名まで含めた完全明細 F1 は 20.00% で、読み取り結果を確認・修正する画面は引き続き必要になる。端末内 OCR の抽出規則も改善し、画像を送信しない選択肢を残した。以下では実写と合成、調整用と未調整の画像、実測と各製品の公式仕様を区別する。

## データセットと分割

取得方法、配布条件、正解の変換規則は [データセット README](../scripts/receipt-datasets/README.md) に記載した。第三者の画像や元の正解をリポジトリへ同梱せず、取得した版とファイルのハッシュを固定する。

| データ                                                                                              | 種類                                   | 取得数 | dev | holdout | 評価から除外 |
| --------------------------------------------------------------------------------------------------- | -------------------------------------- | -----: | --: | ------: | -----------: |
| [JaWildText `receipt_kie`](https://huggingface.co/datasets/llm-jp/jawildtext)                       | 日本語の実写真、Apache-2.0             |     30 |  10 |      11 |            9 |
| [Japan OCR Mini Benchmark Alpha10](https://huggingface.co/datasets/K10124/japan-ocr-mini-benchmark) | 日本語の合成画像、Alpha10 は CC BY 4.0 |     10 |  10 |       0 |            0 |

JaWildText は先頭 10 件を dev、その後の 20 件を holdout として、モデルの結果を見る前に予約した。holdout のうち総額の正解が欠落・判読不能の 1 件、明細の正解が不完全な 8 件を、事前の変換規則に従って画像単位で除外した。モデルの苦手な画像を選んで除外したものではない。除外前の一覧と理由は取得時の記録に残す。

JaWildText の採用 21 件では、正解の数量が空欄だった 32 行を 1 としている。0 円のオプション 15 行は品目評価から除いた。負の値引き行は品目に含めず、印字された総額は保持する規則にしたが、採用分に負の値引き行はなかった。数量をすべて画像から人が確認した評価ではない。

実写には飲食店・スーパー・持ち帰りのほか、玩具・自転車・交通のレシートも含まれる。今回の 21 枚は飲み会の利用場面を代表する無作為標本ではない。合成 10 枚の結果も実写の成績と合算しない。JaWildText の出典は Maeda / Okazaki の [JaWildText 論文](https://arxiv.org/abs/2603.27942)。

CORD は明細の詳細な注釈があるが日本語の評価ではなく、SROIE は主な抽出対象が店名・住所・日付・合計のため数量と明細の評価に不足する。日本語レシートを使った公開モデルも調べたが、モデルのライセンスと学習画像の利用許諾を混同せず、画像と正解の取得・利用条件が確認できた 2 データセットを採用した。各候補の出典は [データセット README](../scripts/receipt-datasets/README.md#比較した別候補) を参照。

## 比較条件

主比較では、同じ元画像に本番の `prepareReceiptImage` を適用する。紙面を検出した場合は切り抜きと多角形のマスクを行い、長辺 3,200 px・192 万画素以内の PNG にする。AI 側は本番画面で元画像を選択し、読み取り後の編集画面から品名・数量・金額・総額を取得する。Tesseract 側は同じ前処理 helper をブラウザーで実行して保存した PNG を読む。ブラウザーは Chrome 153、helper のソースとハッシュは共通だが、AI へ送った Blob と Tesseract 入力 PNG のバイト単位の一致までは照合していない。

対照として、Pillow の LANCZOS で向き・白背景・画素数上限だけを合わせた PNG も評価した。この経路はブラウザーの紙面検出・切り抜きを通さない。Tesseract と REST API へは同じ保存済み PNG を渡し、個別画像の SHA-256 一致を確認した。後述の表でブラウザー経路と区別し、数値を混ぜない。

Tesseract はどちらも Node.js で実行しているため、ブラウザー内でのメモリ量や処理時間の測定ではない。AI には画像と固定した抽出指示だけを送り、正解データは送信しない。

Tesseract は Tesseract.js 6.0.1、日本語＋英語、OEM 1、PSM 6、空白保持、DPI 300。パーサー改善後は保存済みの同じ OCR テキストを再解析した。新しい OCR を都合よく選び直していない。

品名は NFKC 正規化と空白除去後に比較し、行の順番によらず一対一で対応させる。同額・同名の商品が複数あっても、一つの予測行を複数の正解に使い回さない。

- 完全明細 F1: 品名・行金額・数量がすべて一致した行の precision と recall から計算する micro F1。
- 金額・数量 F1: 品名を除いて行金額・数量で照合する補助指標。同額の別商品を区別できないので、これだけを「正確さ」としない。
- 総額一致: 印字された支払総額との完全一致件数。明細の合計から正解を作り直さない。
- 処理失敗: OCR や API、JSON 検証の失敗も分母に残す。失敗画像を落として精度を上げない。

完全一致の指標なので、品名の一文字だけの誤りもその行は不一致になる。文字の一部が読めている割合や、人が修正するのにかかる時間を示す値ではない。評価コードと空集合の扱いは [評価 README](../scripts/receipt-eval/README.md) を参照。

ブラウザーでの前処理は 31/31 枚で成功した。パーサーの前後比較には同じ OCR テキストを使い、旧版 `bf42c29` と改善後のソースを照合した。正解行数は実写 dev 33 行、実写 holdout 21 行、合成 dev 70 行。holdout の個別結果を使った調整はしていない。

この実写群では、ブラウザーの切り抜きを通した Tesseract の成績が、下の Pillow 対照より低かった。自動切り抜きが常に改善するとはいえず、前処理にも検証の余地がある。本番と同じ前処理を主比較にした理由は、現在の利用経路へ条件を合わせるためである。

実写 dev の Gemma は 33 行すべてで金額・数量が一致し、品名まで一致した行は 9/33 行だった。総額は 10/10 枚一致したが、品名の確認・修正は依然として必要になる。画像選択から編集画面への反映確認までの時間中央値は約 5.19 秒、最大は約 13.33 秒。約 1 秒ごとに画面を確認した値で、前処理・往復通信・推論・画面反映・確認待ちを含み、モデル単体の処理時間ではない。10 枚の中央値は中央 2 値の平均から計算した。

プロンプトとモデルを固定した後の実写 holdout では、金額・数量 F1 が 85.00%、総額が 10/11 枚一致した。金額・数量は正解 21 行、予測 19 行のうち 17 行が一致し、precision 89.47%、recall 80.95%。品名まで一致した行は 4 行だった。1 枚は画面に「読み取った内容を確認できませんでした」と表示され、編集結果を取得できなかったため失敗として分母に残した。バックエンドの詳細は取得しておらず、モデル・通信などの原因をこの表示だけから断定しない。中央値は約 5.16 秒、最大は約 10.26 秒だった。個別画像・品目の内容を見て調整し直していない。

合成 dev では、Gemma の金額・数量が 64/70 行、品名まで含めて 57/70 行一致した。総額は 10/10 枚一致し、処理失敗はなかった。時間中央値は約 5.20 秒、最大は約 32.80 秒だった。総額がすべて一致しても各明細がすべて正しいとは限らず、実写の品名一致率とも大きな差がある。

この範囲では Gemma による数値抽出の改善を確認できたため、画像を読む AI 経路のモデルに採用する。全明細の品名が正しくなるわけではなく、未知のレシートや一時的な失敗にも備えて修正画面と端末内 OCR を残す。未実行の Google、Azure、PaddleOCR や、1 枚だけ確認した Qwen より高精度だと結論づけたものではない。

### 参考: REST 通信とモデルの予備確認

本番画面の比較に先立ち、CLI からの REST 呼び出しを検証した。認証失敗で全件 HTTP 401 になった実行は、認識精度を測定できていないため方式の優劣には使わない。実行記録では失敗を分母に残したまま保存し、認証・通信経路を修正した実行を別の出力先へ保存した。

参考として、同じ Pillow prepared image と本番共通プロンプトを使い、Workers AI の REST API へ直接送った実写 dev 10 枚では、完全明細 F1 が 8.33%、金額・数量 F1 が 62.50%、総額が 5/10 件一致した。10 件中 3 件は 45 秒の通信タイムアウト、1 件は返却内容の検証失敗で、いずれも分母に残した。所要時間中央値は約 37.88 秒だったが、実行環境では AI 以外への通信にも DNS・TLS・タイムアウトの障害が見られた。この時間は往復通信を含み、モデル単体の推論時間とは扱えない。本番画面での主比較と混ぜない。

Gemma と Qwen の予備確認には、実写 dev の 1 枚を原寸で使用した。両方とも 7 行の金額・数量と総額が一致し、品名の誤りは残った。応答までの時間は Gemma が約 8.47 秒、Qwen が約 21.99 秒だった。ただし、この確認は本番共通プロンプトや prepared PNG を使ったものではなく、上の固定条件の比較には含めない。1 枚の結果からモデルの優劣や平均速度を結論づけない。

## 実装した抽出と検証

画像 LLM には品名、数量、単価、印字された行金額、総額、別途加減算する税・値引き・料金を分けて返すよう指定する。読み取れない数値は `null` とし、総額に合わせるための品目や金額の追加を禁じる。品名や金額の正しさを、モデルが自己申告する信頼度だけで決めない。

アプリ側で JSON の形、整数の金額、数量 1〜999、明細数、文字数を検証する。単価×数量と行金額の不一致、明細と調整額の合算と総額の不一致は利用者に確認を促し、印字値を勝手に補正しない。内税を追加料金にせず、0 円オプションを商品タイルにしない。不明な金額・数量は修正が必要な下書きの値として扱う。

画像送信が不要な端末内 OCR も残す。AI 経路は縮小後の画像を Worker へ送り、画像とモデルの生出力をアプリの永続ストレージやログへ保存しない設計にした。これは評価用のローカル保存とは別で、評価用ディレクトリには再検証のための生テキストや応答が残る。Cloudflare は、明示的な同意なしに Workers AI の入力・出力を学習やサービス改善へ利用しないと説明している。[公式データ利用方針](https://developers.cloudflare.com/workers-ai/platform/data-usage/)

## 残る課題

今回の実写真は少数で、居酒屋の複数杯・複数皿、長い買い出しレシート、反射、折り目、暗所、複数税率を十分に覆っていない。外部サービスの日本語対応や合成データの高い成績だけで、これらに対応済みとは判断できない。

holdout はこの開発で抽出規則やプロンプトの調整に使わなかった画像を指す。公開画像と各モデルの学習データとの重複は確認できておらず、モデルにとっても初見の画像だったと保証するものではない。

今後の比較では、同じ店舗・同じレイアウトに偏らない追加画像を確保し、飲食用途、撮影条件、数量のある行を分けて集計する。現在の holdout を見て調整した後は、同じ画像を新たな未知データの評価として再使用しない。今回のデスクトップでのブラウザー検証に加え、スマートフォンでの撮影・処理時間、利用者の修正件数も測る必要がある。
